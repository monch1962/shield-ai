Reference Architecture -- SHIELD-AI™ Control Stack

This is the anchor for every pillar. Each numbered area maps to a SHIELD-AI™ pillar.

Agentic AI Threat Landscape

Seven layers of attack surface -- controls must cover all of them

🧠 Model Layer

Prompt injection, jailbreaking, model inversion, data extraction from responses, backdoor triggers

🔧 Tool Layer

Tool output injection, malicious tool registration, API abuse, tool chain poisoning

🔒 Identity Layer

Credential delegation abuse, session hijacking, privilege escalation via agent-to-agent

🛡️ Execution Layer

Sandbox escape, host-trusted file injection, fail-open sandbox fallback, control-plane config poisoning

📊 Data Layer

Cross-session data aggregation, RAG pipeline poisoning, PII leakage in tool calls

🕹️ Pipeline Layer

CI/CD compromise, model update substitution, dependency chain poisoning

🏛 Governance Layer

Shadow AI, uncontrolled agent proliferation, missing audit trails across agent chains

Risk compounds upward: Model compromise enables Tool abuse, which enables Data exfiltration -- and an escaped sandbox invalidates every layer

Why Existing Frameworks Don't Cover Agentic AI

ASD ISM (1,081 controls)

Zero AI-specific controls. March 2026 "Guidelines for secure AI system development" is introductory, not a control framework.

Essential Eight

Necessary but insufficient -- doesn't address prompt injection, tool delegation, agent identity.

NIST AI RMF

Risk management process -- not an implementable control framework. No technical control specifications.

OWASP LLM Top 10

Threat taxonomy, not a framework with maturity levels, implementation guidance, or regulatory mapping.

EU AI Act

Risk classification + obligations. No technical controls defined.

ISO/IEC 42001:2025

AI management system -- defines governance processes, no technical security controls.

MS-06Model inventory & lineage -- catalogue all models, versioning, deployment tracking

Decision Tree: Choosing Your Approach

💡 How to approach model security:
Q: Do you use third-party or self-hosted models?
Third-party -> focus on MS-04 (prompt injection testing), MS-05 (output guardrails)
Self-hosted -> add MS-01 (weight encryption), MS-02 (training integrity)
Q: How many models in production?
<5 -> Manual inventory (MS-06 spreadsheet)
5+ -> Deploy model registry with signing at every stage
Q: Do agents use RAG?
Yes -> Implement RAG security layer for DS-01/DS-04 in parallel
No -> Defer RAG controls to Phase 2

AU Mappings

ISM: secure AI system dev, system hardening, procurement. ASD supply chain guidance (Mar 2026).

IAM-03Human oversight -- approval gates for high-risk actions, break-glass with audit trail

Decision Tree: Choosing Your Approach

💡 Choosing your agent identity approach:
Q: How many agents?
<5 -> OPA sidecar per agent (simplest path)
5-50 -> Central OPA gateway (single policy enforcement point)
50+ -> OPA + SPIFFE/SPIRE for workload identity (scales)
Q: Multi-agent architecture?
Yes -> Add bounded delegation chain (IAM-02 extended)

Yes -> Code execution = highest-class tool: requires human approval for production writes

Decision Tree: Choosing Your Approach

💡 How to approach data security:
Q: Does your agent use persistent memory?
Yes -> DS-03 is highest priority: retention policies, automated purging, per-agent scoping
No -> Defer DS-03, focus on DS-01 (classification) and DS-04 (minimisation)
Q: RAG pipeline?
Yes -> Implement ABAC at retrieval time, field-level redaction before context injection
Q: Regulated data (PII, financial, health)?
Yes -> DS-02 (encryption), DS-06 (output scanning), Privacy Act mapping required

Privacy Act (APP 11, 5, 6). ISM: data transfers, media, crypto. SOCI: CIRMP data obligations. PSPF: sensitive info.

MCP Protocol & Agent-Tool Interface Security

✅ Security Benefits of MCP

Standardised interfaces enable standardised controls. MCP defines tool discovery schemas, typed tool interfaces (JSON Schema), and structured error responses -- making generic tool security proxies possible.

⚠️ MCP Attack Surface

Tool discovery poisoning, capability advertisement manipulation, protocol-level prompt injection through tool descriptions, MCP gateway bypass.

SHIELD-AI MCP Controls

TP-03 extended: MCP gateway enforces auth, schema validation, rate limiting at protocol layer. TP-04 extended: MCP response validation against known-good schemas. MS-04 extended: MCP protocol-layer adversarial testing.

MCP Gateway Architecture

Agent → MCP Gateway (proxy) → Tool Server
          │
          +- Authenticate agent identity
          +- Validate tool discovery response
          +- Enforce allow-list per agent
          +- Validate request/response schema
          +- Rate limit per agent+tool
          +- Audit log every invocation
          +- Fail closed if audit down

Emerging: Multi-Agent Systems & Agent Swarms

Architecture Changes

  • Delegate tasks to other agents -- delegation chains
  • Share context -- one agent's output is another's input
  • Coordinate -- interdependent multi-agent workflows

Blast Radius Multiplier

A single compromised agent poisons every downstream agent's context. Prompt injection impact scales from one tool chain to the entire swarm.

IAM-02: Bounded Delegation Chain

Agent-to-agent must not expand original scope. Each hop respects bounds -- no escalation across delegation chains.

MIR-01: Distributed Tracing

Single user request -> chain of agent calls reconstructable as one audit trail. Requires distributed tracing header propagated across all agents.

TP-01: A2A as Tool Class

Agent-to-agent APIs registered, versioned, security-approved -- same rigour as external tool endpoints.

Timeline

Production 2026. Dominant by 2027-28. L3 clients plan now.

Emerging: Persistent Agent Memory

Data Aggregation Risk

  • Agent remembers User A's financial details
  • User B queries in Session 2 -- cross-reference possible
  • Memory embedding spaces encode sensitive correlations

Attack Vectors

Memory-read: compromised session reads another session's data. Memory poisoning: crafted inputs trigger unintended behaviour on retrieval.

DS-03: Memory Sanitisation (HIGHEST PRIORITY)

Retention policies with automated purging. Cross-session aggregation detection. Per-agent memory scoping. Encryption at rest.

DS-04: Memory Minimisation

Only essential data remembered. Memory scoped per-agent and per-task -- not shared across agents by default.

MIR-02: Memory Access Anomaly Detection

Baseline memory access patterns. Agent accessing weeks-old records = compromise indicator. Cross-agent memory access = policy violation.

Emerging: Autonomous Code Generation

The highest-risk agent capability -- treat accordingly

LevelCapabilityHuman Approval
1Generate SQL queriesAlways
2Generate shell commandsAlways
3Generate config filesAlways
4Self-heal -- patch own codeAlways + sandbox
5Write and deploy microservicesMulti-party approval

TP-01: Code Execution as Tool Class

Distinct class with highest security. Must be explicitly enabled per agent -- never default-on.

TP-04: Code Output Validation

Sandbox-executed and output-verified before production. Human review gate for infra-modifying code.

MIR-04: Code Injection Playbook

Different containment: revoke code-exec tool, rollback affected systems, audit recently generated code.

Deployment Topologies -- Decision Tree

<10 agents

Embedded library -- security controls via agent framework SDK/plugin. Low latency, simple config. Best for: pilots, single-agent PoCs.

Pros

No infra dependency, consistent with framework API

Cons

Framework-dependent, bypassable if agent code modified

10-100 agents

Sidecar proxy -- per-agent sidecar (OPA + tool gateway + telemetry). Best for: K8s deployments, existing service mesh.

Pros

Isolation per agent, no SPOF, consistent with sidecar mesh

Cons

Resource overhead, config drift at scale

100+ / multi-agent

Central gateway + sidecar audit -- gateway for external tools, sidecars for cross-agent monitoring. Best for: enterprise, regulated, multi-agent systems.

Pros

Single policy point, central audit, distributed scale

Cons

Complexity, requires service mesh maturity

Why adopt

Every control is a documented, testable assertion with implementation guidance -- not a policy binder. Deployable components are specified in the implementation architecture document.

Why build fails

The threat landscape moves monthly (CrewAI, Codex CLI, CVE-2026-35603, Langflow KEV, Semantic Kernel). A bespoke framework is obsolete before it ships.

Real-world driver

Sandbox escapes are the #1 incident pattern (7/10 documented cases). Most in-house stacks have no execution-environment controls at all.
